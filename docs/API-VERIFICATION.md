**First actual generation — 19 October 2026 (05:14 WIB / 2026-10-18T21:14Z): PASS.** `make youcam-probe -consent` ran one `cloth-v4` task with `garment_category=upper_body` from this machine (provider connectivity worked this time). Inputs: a front-facing white-background portrait of the user, who confirmed identity and consent for upload to YouCam (resized to 1024×1536 JPEG), and a third-party store image of a short-sleeve printed camp shirt (1024×1024), which the user agreed is for this private test only and must not appear in demo/video/submission. Outcome: task status `success`, measured end-to-end latency 15,184 ms, result JPEG 1024×1536 saved privately under ignored `.data/probe/`. Units were not returned by the response; check the console balance. Visual review: the blazer, tie and shirt were replaced by the reference shirt with matching color, print and collar; face, hair and background were preserved; the source watermark did not appear. This confirms key validity, V4 endpoint entitlement and acceptance of `upper_body`. Task ID, signed URLs, key and images are intentionally omitted.

**First in-app generation — 19 October 2026 (~06:10 WIB): FAILED, not retried.** With `RENDERER_MODE=youcam` and the new Commons photo catalog, the UI flow ran once: SL-001/M/$60 shortlist → SL-002 "Harbor Stripe Popover" → consent → upload of the same consented portrait → one "Create YouCam preview" click. The task was created and reached `task_status=error` after ~30 s (two polls). One later read-only GET of the same task (no new generation) returned `error=error_pose`, "Please ensure that the chest, and shoulders are clearly visible." The person image content was identical to the successful probe (no EXIF orientation; the app re-encodes uploads to PNG). Differences: garment reference (a shirt hanging on a grey wall instead of a flat front product shot) and PNG vs JPEG source encoding. Root cause is not proven. Follow-up: the adapter now keeps only a safe provider error code (`^[a-z0-9_]{1,48}$`) and the UI explains `error_pose`/`error_no_face`; free text and URLs are discarded. The preview slot remains consumed by design.

**Second in-app generation — 19 October 2026 (~06:58 WIB): FAILED, not retried.** User approved one more attempt. Same flow with SL-003 "Graphite Check Shirt", a flat white-background product photo. The task again ended with `error_pose` after ~20 s, which weakens the garment hypothesis. **Likely root cause found offline:** the app's upload normalizer re-encoded the decoded JPEG (YCbCr) with Go's `png.Encode`, which writes non-RGBA images as **16-bit-per-channel PNG**; pixel content matched the source (RMSE 0.0013), but the successful probe had sent the original 8-bit JPEG. Fix: normalize into an 8-bit NRGBA image before encoding, with a regression test on the PNG IHDR bit depth. Upload-only verification after rebuild (no generation): the stored copy of the same portrait is now `PNG 1024x1536 8-bit sRGB`. Not yet confirmed by a successful in-app generation.

**Third in-app generation — 19 October 2026 (~07:10 WIB): PASS.** User approved one more attempt after the 16-bit PNG fix. Same flow, SL-003 "Graphite Check Shirt", same consented portrait. One click; task `success` after one poll, ~14 s job time (created → updated). The UI showed "YOUCAM · AI PREVIEW" and "Provider preview received."; the result is stored privately in the app (8-bit PNG 1024×1536) and a copy was saved to the user's Downloads at their request. This confirms the end-to-end app path (upload with consent → private storage → YouCam cloth-v4 upper_body → polling → private result) and supports the 16-bit PNG root cause. In-app tally: 3 generations attempted, 1 success, 2 `error_pose` before the fix; units per task not reported by the API.
